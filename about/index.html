01 纯静态，零依赖

整个站是纯 HTML / CSS / JavaScript，没有构建步骤、没有框架、没有 npm 依赖。 改完直接推送到 main，GitHub Pages 立刻发布。

  • 没有打包器，所以不存在「本地能跑、线上白屏」这类构建差异
  • 没有第三方运行时，所以不存在依赖被下架或改协议导致站点挂掉
  • 体积小、首屏快，任何静态托管都能跑，换平台不需要改代码

代价是很多东西要自己写（比如主题切换、双语、命令面板）。 但我更愿意为自己的代码负责，而不是为一堆依赖的升级节奏负责。

02 一份变量，十九个页面

最初每个页面各写各的颜色：有的是 #D4AF37（金），有的是 #2563EB（蓝），有的是 #14B8A6（青）。 于是「换一次配色」要改十九个文件，而且必然改漏。

现在全站只有一份 assets/theme.css，所有颜色都以 CSS 变量定义， 19 个页面在 </head> 前引用它。换配色只改这一个文件。

这里踩过一个不明显的坑：子页面内部往往也有自己的 :root[data-theme="dark"]，它的选择器特异性更高， 所以无论加载顺序如何都会把共享文件压过去。 解决办法是让共享文件用同等特异性（:root, :root[data-theme="dark"]）， 再靠「最后加载」取胜 —— 这一点写进了文件的注释里。

03 双语不加标记

常见做法是给每个待翻译元素加 data-i18n="key"。 但本站有 19 个页面、几百条文案，逐条标记既慢又必然漏， 漏掉的地方就会出现「切了语言但那段还是中文」。

所以我用了另一种方式：进入页面时先用 TreeWalker 把每个文本节点的 原文记下来，切换语言时按「原文 → 译文」查表替换，切回中文时按记下的原文还原。 好处是加译文只改一个文件，且不需要动 HTML。

两个刻意的设计：未收录的条目保持原文（宁可留中文，也不要半吊子机翻）； 运行时才出现的文字也能翻 —— 用一个只监听 childList 的 MutationObserver 接管新节点。之所以不监听 characterData， 是因为我们修改文本本身就会触发它，一起监听会自触发、陷入死循环。

04 一次真实的排障：亮色主题整块失效

现象是「切换深浅色没反应」。我一开始怀疑切换逻辑写错了，于是在真实浏览器里点了一次， 量出来的结果很反常：

  • data-theme 确实从 dark 变成了 light
  • 偏好也确实写进了本地存储
  • 但 --bg 纹丝不动，仍是 #0b0e14
  • 而且用 CSSOM 统计，含 data-theme="light" 的规则数为 0

也就是说：切换逻辑是好的，是亮色那套 CSS 根本没被浏览器解析。 顺着这条线找到根因 —— 基础 :root 块闭合之后， 有 6 条 --glass-* 声明「无主」地留在了样式表顶层：

CSS 不允许声明出现在规则之外。浏览器做错误恢复时，会把这些声明当作 「下一个规则的选择器前奏」一路读下去，于是紧随其后的 :root[data-theme="light"] { … } 整块被当成无效规则丢弃。

修法是把那 6 条声明搬回 :root 内部。修好后实测： 亮色下 --bg 变为 #f6f8fc、页面背景变为 rgb(246,248,252)，恢复正常。

这个 bug 早于我的改版就存在 —— 我用改版前的提交对照过，同样的位置、 同样的结构。所以它不是「改坏的」，而是一直坏着、只是没被触发到。

05 先量再改

这个站改到现在，我犯过不少错，其中绝大多数是「靠猜」犯的。 举三个我自己推翻自己的例子：

  • 怀疑某张卡片看不见是 --card-image 被当成文字渐变 —— 一查，站内根本没有那种写法
  • 怀疑某页溢出来自 512×512 的预览画布，因为「512 − 可用宽度 355 = 157」与实测溢出完全吻合 —— 加了限宽后数值纹丝不动，纯属数字巧合
  • 连续四轮报告某三页「语言按钮文案不切换」，最后发现是我的探针用脚本模拟点击、而按钮需要真实手势才响应 —— 页面一直是对的

还遇到过一次更根本的问题：移动端的溢出量同一份代码测三次得到 87 / 132 / 157 三个数。 查下去才发现是探针「加载后固定等 450 毫秒」就测量，抓到了脚本渲染的中间状态。 改成反复采样、直到数值连续 5 次不变之后再读，同一配置连测三次结果完全一致 —— 尺子准了，后面的判断才第一次有了依据。

结论：测量工具本身也要被验证。 尺子不准的时候，改得越多、错得越远。
